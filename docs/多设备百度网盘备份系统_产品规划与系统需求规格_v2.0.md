# 0. 执行摘要

本产品是一款面向同一用户多台电脑的**版本化、去重、增量、可加密、可验证恢复的备份管理软件**。百度网盘是首个远端存储目标，但产品的数据模型、快照协议、备份状态、恢复逻辑和安全能力不与百度网盘目录结构强绑定。

产品解决的核心问题不是“把文件上传到网盘”，而是：

1. 多台电脑中存在大量内容相同但路径、文件名不同的文件，如何避免重复上传和重复占用。
2. 如何明确知道每一个文件和文件夹“当前版本是否真正受保护”。
3. 如何区分“其他设备已有相同内容”和“本机路径已经进入可恢复快照”。
4. 如何同时支持原样、压缩、加密、压缩+加密四种存储要求。
5. 如何进行可靠的增量扫描、断点续传、多设备协同、历史版本和灾难恢复。
6. 如何在误删、勒索软件、云端对象丢失、客户端崩溃、原设备损坏等情况下仍能恢复。
7. 如何保证未来可扩展到其他云存储，而不是把备份核心锁死在百度网盘。

正式产品的基本判断标准是：

> **只有一个文件的当前版本、路径关系、策略要求、所需对象和清单均已成功提交，并且不存在已知恢复阻断时，才能显示“当前版本已备份”。**

# 1. 产品定位与边界

## 1.1 一句话定义

面向个人、家庭及小型工作组的多设备备份系统：使用内容指纹识别重复数据，在同一受信任仓库内跨设备复用已存在的兼容内容，保留各设备的原始目录结构与历史版本，并提供可解释的保护状态、完整性验证和灾难恢复能力。

## 1.2 建议默认产品边界

| 事项 | 默认方案 |
| --- | --- |
| 产品性质 | 备份系统，不是双向工作文件同步盘 |
| 首发平台 | Windows |
| 用户模型 | 同一所有者或同一受信任小组 |
| 设备规模 | 暂按 3–10 台设计和验证 |
| 云端目标 | 首期一个百度网盘账号、一个或多个逻辑 Repository |
| 数据方向 | 多设备 → 共享备份仓库 |
| 去重范围 | 默认同一 Repository、同一安全域内跨设备去重 |
| 删除语义 | 本地删除不立即物理删除云端历史 |
| 增量层级 | 正式 v1 先保证文件级增量；块级增量后置 |
| 多设备协调 | 首版无常驻自建服务器；必要时后续增加协调服务 |
| 恢复 | 原设备离线甚至丢失时仍应可从远端重建 |
| 本地去重清理 | 不纳入默认备份产品范围 |
| 双向文件同步 | 独立产品评审，不与备份语义混合 |

## 1.3 明确不做或不默认做

- 不把 A 电脑的工作文件自动同步下载到 B 电脑。
- 不因为本机文件删除就自动永久删除远端历史版本。
- 不自动删除用户电脑上的重复文件。
- 不宣称提供整机裸机恢复。
- 不宣称所有正在运行的数据库仅靠文件复制即可获得业务一致备份。
- 不在互不信任用户之间进行全局去重。
- 不依赖抓取 Cookie、借用不明 App 凭据、绕过平台限制等非正式能力。
- 不把百度网盘中的普通目录结构当成本产品唯一的备份数据库。

## 1.4 三个必须向用户说明的承诺边界

**已上传过不等于现在仍然可恢复。**  
远端对象可能被删除或损坏，恢复密钥也可能遗失，因此界面必须同时展示提交状态、远端健康和最后验证时间。

**不重复备份不等于任何异常情况下都绝不产生重复流量。**  
正常情况下已存在且兼容的内容不重传；但并发首次上传、网络重试、上传会话失效等情况仍可能产生临时重复传输。系统优先保证不丢数据和可恢复。

**加密仓库不等于普通网盘目录体验。**  
压缩、加密、去重和版本化需要由本产品维护清单与对象关系。是否要求在百度网盘原生客户端中按原目录直接浏览，属于另一条产品路线。

# 2. 原始需求与需求编号

## 2.1 用户明确需求

| 编号 | 需求 |
| --- | --- |
| U01 | 多台电脑存在大量重复文件和重复文件夹，需要统一备份到百度网盘 |
| U02 | 已经备份过的内容默认不重复上传 |
| U03 | 显示文件和文件夹的备份状态，并支持按状态筛选 |
| U04 | 区分未备份、已备份、本机备份过、其他设备备份过等情况 |
| U05 | 支持直接备份、压缩备份、加密备份、压缩加密备份 |
| U06 | 支持增量备份、多设备协同、断点续传、文件恢复 |
| U07 | 需要补齐遗漏功能并形成可交付的产品规划 |
| U08 | 多设备间应共享“哪些内容已经保护”的信息，而不是互相同步工作文件 |
| U09 | 需要长期可维护、可扩展，后续可对接其他存储目标 |

## 2.2 规划假设

当前暂按以下假设设计，不代表已经最终确认：

- Windows 优先。
- 个人自用、家庭或同一所有者的小型设备群。
- 仓库累计可达到百万级路径记录和 TB 级逻辑数据。
- 首期主要使用一个百度网盘账号。
- 同一 Repository 内设备共享信任与仓库密钥。
- 不要求多设备形成同一时刻的事务一致快照。
- 首期不依赖常驻协调服务器。

# 3. 核心产品原则

| 原则 | 解释 |
| --- | --- |
| 备份优先于同步 | 误删、覆盖、勒索和设备损坏都需要历史恢复能力 |
| 内容寻址而非路径寻址 | 路径用于恢复位置，内容身份由稳定摘要决定 |
| 路径登记与内容存在分离 | “云端已有内容”不代表“本机路径已经备份完成” |
| 状态必须可解释 | 任何未保护、失败、跳过、复用状态都要给出原因和下一步 |
| 策略满足才算已保护 | 已有明文不能满足当前“必须加密”的要求 |
| 恢复能力优先 | 能上传但不能验证恢复，不算完成备份 |
| 元数据必须可重建 | 本机 SQLite 丢失后仍能从远端 Manifest 重建 |
| 不可变数据优先 | 数据对象和已提交快照尽量不可变，降低多设备并发风险 |
| 安全优先于绝对去重 | 不为减少一份对象而破坏加密要求或恢复可靠性 |
| 云存储适配解耦 | 百度网盘是 Storage Adapter，不是业务模型本身 |
| 未验证的云端原子能力不可依赖 | G0 未验证前，不用“锁文件”假装分布式锁 |
| 删除比上传更保守 | GC/永久删除必须证明对象无任何保留引用 |

# 4. 核心场景

| 场景 | 预期行为 |
| --- | --- |
| A 已备份，B 存在同内容异名文件 | B 完成强内容确认后复用已有 Representation，仅登记 B 的路径与快照 |
| 文件名相同、内容不同 | 作为不同 Content，不允许误跳过 |
| 文件名不同、内容相同 | 在策略兼容时复用 Content/Representation |
| 文件备份后发生修改 | 当前版本显示待保护，同时保留历史版本 |
| 文件仅改名/移动 | 内容未变时不重传数据，只更新路径关系 |
| 文件夹整体复制 | 相同文件内容复用，新的目录结构单独登记 |
| 两设备同时首次上传相同内容 | 允许暂时产生冗余 Object，但不能覆盖或错误引用 |
| 外接硬盘被拔出 | 标记源离线，不推断该盘内容被用户删除 |
| 云端对象被人工删除 | 受影响版本标记风险；有可靠源副本时可自愈 |
| 明文策略改为加密 | 旧明文不视为满足；创建新的安全 Representation |
| 原设备与本地数据库全部丢失 | 新设备凭 Repository 和恢复材料重建快照并恢复 |
| 短时间大量文件被改写或删除 | 触发异常保护，保留异常前健康恢复点并要求用户确认 |

# 5. 术语与核心数据模型

## 5.1 核心术语

**Repository / 仓库**  
一个逻辑隔离的备份空间，拥有独立 ID、格式版本、安全域、密钥体系和远端定位。

**Device / 设备**  
一台已加入 Repository 的电脑，使用稳定随机 device_id 标识。

**BackupPlan / 备份计划**  
某设备上的一个或多个备份根目录，以及包含/排除、存储策略、计划、保留和资源规则。

**FileInstance / 文件实例**  
某设备某备份根目录中的一个具体路径条目。两个设备上的相同内容仍是两个 FileInstance。

**Content / 原始内容**  
由原始文件内容定义的逻辑身份，例如 SHA-256 + 原始长度。

**Representation / 存储表示**  
同一个 Content 经不同压缩、加密、密钥版本、格式版本处理后得到的可存储形式。

**Object / 物理对象**  
真正写入百度网盘或其他 Storage Adapter 的远端对象。一个 Representation 可因并发等原因临时对应多个物理 Object。

**Snapshot / 快照**  
某设备、某 BackupPlan、某时间点的完整逻辑恢复视图。

**SnapshotEntry / 快照条目**  
快照中的具体文件、目录、空目录、元数据、排除或错误记录。

**Manifest / 清单**  
描述 Snapshot、目录结构、Representation/Object 引用和完整性信息的结构化数据。

**Verification / 验证记录**  
针对 Object 或 Snapshot 执行的提交确认、抽样恢复、完整恢复验证结果。

**内容块**  
用于文件内部去重或独立加密的数据块。

**上传分片**  
云服务上传协议中的网络分片。上传分片不等于块级增量。

## 5.2 推荐关系模型

```text
Repository
 ├─ Device
 ├─ BackupPlan
 │   └─ FileInstance
 │       └─ Content
 │           └─ Representation
 │               └─ Object
 ├─ Snapshot
 │   └─ SnapshotEntry
 ├─ Job / UploadSession
 ├─ Verification
 └─ AuditEvent
```

## 5.3 为什么必须拆分 Content、Representation、Object

同一份原始内容可能同时存在：

```text
Content: SHA256 = X
 ├─ Representation A：原样
 │   └─ Object A1
 ├─ Representation B：zstd level 3
 │   └─ Object B1
 ├─ Representation C：XChaCha20-Poly1305，key_epoch=1
 │   └─ Object C1
 └─ Representation D：zstd + XChaCha20-Poly1305，key_epoch=2
     └─ Object D1
```

因此“内容相同”不意味着“已经满足当前备份策略”。

# 6. 去重模型

## 6.1 去重范围

默认仅在以下条件全部成立时复用：

- 同一 Repository。
- 同一受信任安全域。
- Content 已可靠确认相同。
- 目标 Representation 与当前 BackupPlan 策略兼容。
- 所引用 Object 当前没有已知恢复阻断。
- Manifest/索引确认该 Representation 已成功提交，而不是仅处于上传中。

默认不跨 Repository、不同独立密钥域或不同账号隐式去重。

## 6.2 文件识别流程

建议采用两阶段策略：

1. **快速变化检测**：大小、mtime、文件系统 file-id/inode、历史扫描记录、文件系统日志等。
2. **最终内容确认**：对于新增、首次跨设备匹配、存在变化疑点的文件，稳定读取并计算完整强摘要。

强摘要首选成熟 SHA-256 实现。未来可评估 BLAKE3 用于本地高性能扫描，但仓库格式必须记录算法名称和版本。

不得仅凭以下条件判定两个文件相同：

- 文件名相同。
- 路径相同。
- 文件大小相同。
- 修改时间相同。
- 短采样指纹相同。

## 6.3 快速扫描与严格模式

快速模式用于减少重复读取，但必须定期进行强制内容复核。  
当源文件系统无法提供可信变化证据时，应允许用户选择严格模式，即重新读取并计算完整摘要。

## 6.4 Representation 兼容矩阵

| 已有表示 → 当前要求 | 默认行为 |
| --- | --- |
| 原样 → 原样 | 可复用 |
| 明文 → 加密 | 不满足，创建加密 Representation |
| 加密 → 原样且要求网盘原生可读 | 不满足，需另建明文 Representation |
| 已压缩 → 相同算法/参数 | 可复用 |
| 未压缩 → 强制压缩 | 创建压缩 Representation |
| 未压缩 → 自动压缩 | 根据收益检测决定是否新建 |
| 加密 key_epoch 不同 | 默认不隐式跨版本复用，按密钥兼容策略决定 |
| 不同 Repository | 不隐式复用 |

## 6.5 文件夹去重

文件夹不是单个二进制内容对象，而是目录结构与文件引用集合。

可提供两个概念：

**结构相同**：相对路径、文件内容、空目录和选定元数据一致。  
可用稳定目录清单摘要或 Merkle Tree 优化比较。

**内容集合相同但结构不同**：文件内容相同，但文件名或层级不同。  
可作为“重复内容”提示，但不得合并目录结构。

# 7. 备份状态模型

## 7.1 不使用一个枚举字段表达所有状态

状态应至少拆为五个维度。

| 维度 | 候选状态/属性 |
| --- | --- |
| 当前版本保护 | 未扫描、待识别、未备份、可复用待登记、已保护、已修改待备份、排除、源不可读、源离线 |
| 任务执行 | 空闲、排队、扫描、哈希、转换、上传、校验、提交、暂停、失败、取消 |
| 历史与来源 | 有无历史版本、本机是否登记、其他设备是否登记、实际上传来源 |
| 仓库健康 | 已确认、待复核、抽样验证通过、完整验证通过、对象缺失、损坏、权限失效、密钥不可用 |
| 新鲜度 | 最后扫描、最后提交、最后远端同步、最后健康检查、最后恢复验证 |

## 7.2 “本机备份过”和“其他设备备份过”不是互斥状态

例如：

```text
当前版本：已保护
本机登记：是
其他设备登记：办公室电脑、旧笔记本
实际首次上传：办公室电脑
远端健康：已确认
最后完整验证：尚未执行
```

UI 中建议以“当前保护状态”为主标签，其余维度用来源徽标、健康徽标和详情字段显示。

## 7.3 “可复用待登记”

当 B 设备发现 A 已存在相同兼容 Representation 时：

- B 无需重复上传数据。
- 但 B 的 FileInstance 还没有进入 B 自己成功提交的 Snapshot。
- 因此此时不能显示“本机当前版本已保护”。
- 状态应显示：**内容已存在 / 可复用，待登记**。

只有 Manifest/Snapshot 成功提交后才变为已保护。

## 7.4 “当前版本已保护”的判定

必须同时满足：

1. 已确认当前 FileInstance 的内容或可靠源版本证据。
2. 当前路径已写入成功提交的 Snapshot。
3. 所需 Representation 已存在并满足 BackupPlan 策略。
4. 所有必需 Object 已完成远端确认。
5. 当前没有已知 Object 缺失、损坏、权限或密钥阻断。
6. 快照清单自身完整且可解析。

# 8. 文件夹聚合状态

设：

- `N` = 当前扫描范围内应纳入保护的普通文件实例数。
- `P` = 当前版本已经满足保护条件的实例数。

展示：

```text
文件覆盖率 = P / N
字节覆盖率 = 已保护原始字节 / 应保护原始字节
```

还要单独显示：

- 排除数量。
- 不可读数量。
- 未识别数量。
- 空目录是否已登记。
- 目录元数据是否已提交。
- 源是否离线。
- 是否存在云端健康异常。

只有在扫描完整、`N=P`、目录结构和必要元数据已提交、无阻断项时，才显示“全部已保护”。

当 `N=0` 时：

- 真正空目录且已进入快照 → “空目录已保护”。
- 所有内容都被排除 → “无纳入保护内容”。
- 尚未扫描 → “未知”。
- 读取失败 → “无法确认”。

# 9. 状态筛选与全局重复视图

## 9.1 文件/目录筛选

必须支持组合筛选：

- 当前保护状态。
- 任务执行状态。
- 本机是否登记。
- 其他设备是否登记。
- 实际上传来源设备。
- 是否存在历史版本。
- 文件类型。
- 大小范围。
- 最近修改时间。
- 最近成功备份时间。
- 存储模式。
- 错误类别。
- 是否重复内容。
- 仓库健康状态。
- 最后验证时间。

不同维度之间取交集，同一维度多选取并集。

## 9.2 全局重复视图

这是本产品的重要差异化页面。

按照 Content 聚合所有 FileInstance：

```text
内容：SHA256: ...
原始大小：428 MB
逻辑副本：3
兼容 Representation：1
物理 Object：1

├─ 办公室电脑 D:\资料\a.pdf
├─ 家里电脑 E:\Backup\a-copy.pdf
└─ 笔记本 C:\Downloads\document.pdf
```

用户可以看到：

- 同内容存在于哪些设备。
- 共有多少逻辑副本。
- 实际保存多少 Representation / Object。
- 因跨设备去重节省的理论逻辑容量。
- 哪些副本只是可复用但尚未登记。
- 哪些副本因为策略不同仍需产生新 Representation。

该页面仅用于理解和管理备份，不默认提供“一键删除本地重复文件”。

# 10. 四种备份模式

| 模式 | 数据链路 | 优点 | 约束 |
| --- | --- | --- | --- |
| 原样备份 | 原始字节 → 上传 | CPU 开销低、恢复直接 | 内容明文；不保证网盘目录即原目录 |
| 压缩备份 | 压缩 → 上传 | 节省部分空间和流量 | 媒体/压缩包收益低；恢复需解码 |
| 加密备份 | 认证加密 → 上传 | 内容保密 | 无有效密钥无法恢复 |
| 压缩加密 | 压缩 → 认证加密 → 上传 | 兼顾体积和隐私 | CPU/缓存开销更高 |

## 10.1 压缩规则

不建议持续备份时把整个变化频繁的大目录每轮打成一个巨型 ZIP/7z。

正式仓库应优先采用：

- 单文件压缩；或
- 有界对象/块压缩。

可提供“自动压缩”：

- 对文本、文档、数据库导出等候选做压缩收益检测。
- 对视频、图片、已有压缩包等通常直接跳过压缩。
- 如果压缩收益不足，标记“已评估，未压缩”，而不是伪装成强制压缩完成。

ZIP/7z 更适合作为“导出归档”能力，而不是持续增量仓库的默认格式。

## 10.2 压缩顺序

压缩必须发生在加密之前：

```text
原始内容 → 压缩 → 加密 → 远端 Object
```

# 11. 加密与密钥体系

## 11.1 基本原则

- 不自行设计密码算法。
- 使用成熟认证加密（AEAD）库。
- 候选包括 XChaCha20-Poly1305 或经过安全评审的 AES-GCM 方案。
- 仓库主密钥随机生成。
- 用户口令用于封装主密钥，而不是直接作为数据加密密钥。
- 口令派生可评估 Argon2id。
- 每个独立加密单元必须满足 nonce 唯一性要求。
- 不为了去重而固定 nonce。
- 不直接使用内容摘要作为数据加密密钥。

## 11.2 对象查找标识

不建议直接把明文 SHA-256 暴露为远端文件名。

可以采用仓库范围内的带密钥查找标识，例如：

```text
object_lookup_id = HMAC(K_index, content_hash || representation_profile)
```

具体格式由安全评审冻结。

## 11.3 元数据隐私

加密模式建议支持：

- 文件内容加密。
- Manifest 加密。
- 原始文件名和目录结构加密。
- 敏感备注/标签加密。

仍需明确不能完全隐藏的元数据可能包括：

- 对象大小。
- 对象数量。
- 上传时间。
- 访问频率。
- 同一仓库内部的相等关系。

## 11.4 密钥生命周期

建议包含：

- Repository Master Key。
- 密钥封装版本。
- `key_epoch`。
- 恢复码/恢复包。
- 新设备授权。
- 密钥轮换。
- 设备退出/吊销流程。

修改用户口令通常只应重新封装主密钥。  
真正密钥泄露后的轮换可能需要迁移历史 Representation，不能用“改密码”代替。

# 12. 增量备份

## 12.1 三类“增量”必须区分

| 层级 | 定义 | 版本规划 |
| --- | --- | --- |
| 扫描增量 | 优先扫描发生变化的路径 | 正式 v1 |
| 文件级增量 | 未变文件不重传，变化文件形成新完整 Representation | 正式 v1 |
| 块级增量 | 大文件局部变化只上传变化块 | v1.1/V2，视用户数据类型前置 |

**断点续传不等于块级增量。**

## 12.2 Windows 变化检测

可评估：

- USN Journal。
- ReadDirectoryChangesW。
- 周期性全量/抽样复核。

持续监听仅用于优化，不应成为唯一正确性来源。  
文件系统事件丢失或日志溢出时应退化为范围扫描。

## 12.3 稳定读取

对于正在变化的文件：

1. 读取前记录源版本证据。
2. 读取内容。
3. 读取后再次验证源版本。
4. 若期间变化，则当前读取不标记为成功版本。
5. 延迟后重试。

需要严格时点一致性时，可评估 Windows VSS；但不能宣传 VSS 自动解决所有数据库一致性问题。

## 12.4 重命名与移动

内容未变化时：

- 不创建新的 Content。
- 不重传 Representation。
- 仅提交新的路径和元数据关系。

# 13. 多设备协同

## 13.1 默认模式：无常驻服务器

每台设备：

- 拥有独立本地数据库。
- 只写入带唯一 ID 的不可变或追加式索引片段。
- 定期获取其他设备新 Manifest / Index Delta。
- 在本地合并查询视图。

禁止让多台电脑通过网盘反复覆盖同一个共享 SQLite 文件。

## 13.2 正常上传前复用检查

上传前再次检查：

1. 是否已有成功提交的兼容 Representation。
2. 是否存在健康 Object。
3. 当前是否只有“其他设备正在上传但尚未提交”的候选。

未提交对象不能直接当作已备份对象。

## 13.3 并发首次上传

在没有协调服务时：

- A、B 同时首次遇到同一个 Content。
- 允许二者各自安全上传形成 Object A、Object B。
- 两个 Object 都不得覆盖对方。
- 两个 Snapshot 都必须引用可恢复对象。
- 后续维护阶段可合并引用并回收冗余。

优先级：

```text
数据可恢复 > 一致性正确 > 最终去重 > 零重复网络字节
```

## 13.4 不使用未经验证的“网盘锁文件”

G0 没有确认以下能力之前：

- 原子 create-if-not-exists。
- CAS。
- 原子 rename。
- 强一致列表。
- 条件更新。

不得把远端“locks/”目录或锁文件设计为分布式一致性的基础。

## 13.5 可选协调服务

当设备数、多设备并发或“尽量避免重复首次上传”的要求提高时，可以增加 Coordination Service。

职责可包括：

- Content 上传预约。
- 有期限 lease。
- 提交序列。
- 幂等请求记录。
- 设备状态。
- 维护屏障。
- GC 安全协调。

文件正文仍可由客户端直接上传百度网盘，协调服务只保存最少必要元数据。

# 14. Storage Adapter 抽象

备份核心不直接依赖百度 API，定义统一远端存储接口。

候选能力：

```text
StorageAdapter
 ├─ authorize()
 ├─ capabilities()
 ├─ statObject()
 ├─ createUpload()
 ├─ uploadPart()
 ├─ commitUpload()
 ├─ downloadRange()
 ├─ listPrefix()
 ├─ putImmutable()
 ├─ deleteObject()
 └─ quota()
```

百度网盘实现为：

```text
BaiduPanAdapter : StorageAdapter
```

未来可以增加：

```text
S3Adapter
OneDriveAdapter
WebDAVAdapter
NASAdapter
OtherCloudAdapter
```

仓库协议应记录 Adapter 类型、远端 locator 和能力版本，但 Snapshot 的逻辑结构不应依赖具体厂商 API。

# 15. 备份事务模型

## 15.1 完整流程

```text
源可用性检查
→ 扫描与范围固定
→ 稳定读取
→ 内容摘要
→ 去重/策略判断
→ 生成 Representation
→ 上传缺失 Object
→ 远端确认
→ 写完整 Manifest
→ 提交 Snapshot
→ 更新 FileInstance 保护状态
```

## 15.2 上传 100% 不等于备份完成

以下情况不能显示“已保护”：

- Object 已上传但未确认。
- Object 已确认但 Manifest 未写成功。
- Manifest 已写但 Snapshot 提交记录未成功。
- Snapshot 提交成功，但已知 Object 损坏。
- Snapshot 成功，但当前策略要求已经发生变化。

UI 建议单独展示：

```text
上传：100%
提交：处理中
当前版本：尚未完成保护
```

## 15.3 不可变对象

已提交的数据 Object 默认不可原地修改。  
产生新内容、新加密版本、新压缩参数时，创建新 Representation/Object。

# 16. 断点续传与持久化任务

## 16.1 本地必须持久化

至少记录：

- job_id。
- Repository / Device / BackupPlan。
- 源版本证据。
- Content ID。
- Representation 配置。
- 临时对象位置。
- upload session。
- 已确认上传分片。
- 分片校验。
- 重试次数。
- 当前阶段。
- 提交幂等 ID。
- 最近错误。

## 16.2 断点原则

以服务端确认结果为准。  
“客户端曾经发送过”不能等于“服务端已经持久化”。

上传会话失效时：

- 可以重新创建当前 Object 上传。
- 不应重传已经独立确认完成的其他 Object。
- UI 应说明实际重传范围。

## 16.3 压缩/加密续传

如果一个 Representation 正在上传：

- 优先继续上传同一份稳定编码后的字节。
- 不允许重新加密不同内容后继续使用旧分片状态。
- 临时 Representation 应有本地磁盘配额。
- 暂存丢失时安全重建当前对象，不产生假成功。

# 18. 历史快照与保留策略

## 18.1 默认原则

本地文件删除或改变时，不覆盖历史快照。

推荐评审默认值：

- 最近 30 个每日恢复点。
- 12 个每周恢复点。
- 12 个每月恢复点。
- 用户锁定的快照永久保留，直到明确解锁。
- 每个长期离线设备至少保留最后一个完整成功恢复点。

这些默认值需用户确认。

## 18.2 本地删除

只有以下条件成立，才能在新 Snapshot 中记录“该路径不再存在”：

- 备份根目录在线。
- 扫描完整成功。
- 不是权限失败。
- 不是外接盘离线。
- 不是排除规则变化导致的不可见。

历史 Snapshot 仍保留原文件。

## 18.3 物理垃圾回收

Object 只有在以下条件都成立时才能删除：

- 不被任何保留 Snapshot 引用。
- 不被任何在途事务引用。
- 相关 Repository 维护状态已经稳定。
- 多设备写入者满足安全维护边界。
- 删除前重新计算可达性，而不是只相信可能过期的引用计数。

正式首版建议：

> **只提供空间分析和待清理预览，不默认自动物理删除。**

# 19. 异常/勒索软件保护

## 19.1 产品目标

该能力用于降低批量误操作或勒索加密后“新坏版本快速覆盖恢复点”的风险，但不宣传为不可变存储或绝对防勒索。

## 19.2 可检测信号

可以组合检测：

- 短时间大量文件修改。
- 扩展名批量改变。
- 大量文件内容熵明显升高。
- 短时间大量删除。
- 同一目录结构中异常比例骤升。
- 多个 BackupPlan 同时出现异常变更。

## 19.3 保护模式

达到风险阈值后可：

1. 标记当前变化批次为“可疑”。
2. 保存异常前最后健康 Snapshot 为保护点。
3. 暂缓自动执行历史清理。
4. 可选暂停自动提交新正常恢复点，等待用户确认。
5. 明确告警受影响目录和数量。
6. 用户确认后允许继续备份，但保留风险标识。

## 19.4 安全边界

- 该能力不能阻止攻击者删除同一百度账号中的远端数据。
- 共享账号不是强隔离安全边界。
- 重要数据仍建议保留第二独立介质或第二存储目标。
- 不把“多个副本都在同一个百度账号”宣传为独立灾备。

# 20. 完整性、健康检查与自愈

## 20.1 验证等级

| 等级 | 实际检查 | UI 文案 |
| --- | --- | --- |
| V1 提交确认 | Object 存在、Manifest 结构与引用满足提交协议 | 已备份，尚未完整读取验证 |
| V2 抽样恢复 | 下载部分对象并完成解码和原始摘要校验 | 抽样恢复验证通过 |
| V3 完整恢复验证 | 对选定 Snapshot 全部数据执行读取、解码和原始摘要验证 | 完整恢复验证通过 |

验证结论只代表对应时间和范围。

## 20.2 健康巡检

可执行：

- Repository 元数据检查。
- Manifest 引用闭包检查。
- Object 存在性检查。
- 远端对象大小/可用服务端摘要检查。
- 抽样读取验证。
- 用户选择的完整 Snapshot 验证。

## 20.3 自愈

如果：

- Manifest 引用 Object 缺失或损坏；
- 本机或其他已授权设备仍存在已确认相同 Content；

则允许创建修复任务，重新生成兼容 Representation 并恢复可用引用。

自愈结果必须记录 AuditEvent。

# 21. 恢复系统

## 21.1 恢复粒度

支持：

- 当前版本。
- 历史版本。
- 单文件。
- 多文件。
- 文件夹。
- BackupPlan。
- Snapshot。
- 某设备的完整备份范围。

## 21.2 浏览方式

```text
Repository
→ Device
→ BackupPlan
→ Snapshot 时间
→ 目录树
```

并提供：

- 全局文件名/路径搜索。
- 历史版本时间线。
- 仅显示变化。
- 根据健康状态过滤。

## 21.3 恢复目标

- 原路径。
- 新目录。
- 新设备映射路径。

默认建议“恢复到新目录”或“保留两者”。

覆盖现有文件必须单独确认。

## 21.4 恢复流程

```text
选择恢复点
→ 解析 Manifest
→ 检查密钥
→ 检查 Object 健康
→ 估算下载量和目标空间
→ 冲突预览
→ 下载/续传
→ Object 校验
→ 解密/解压
→ 原始 Content 校验
→ 写入临时文件
→ 原子/安全落盘
→ 恢复支持的元数据
→ 生成报告
```

任何校验失败的文件都不得以最终原文件名留下半成品。

## 21.5 特殊路径安全

恢复时所有 Manifest 路径视为不可信输入：

- 防止 `../` 目录穿越。
- 防止绝对路径越界。
- 防止危险符号链接跳转。
- 防止恶意压缩膨胀。
- 处理 Windows 保留名称。
- 处理大小写冲突。
- 处理 Unicode 正规化差异。
- 处理长路径。
- 必要时生成重命名映射报告。

# 22. 全新设备灾难恢复

这是正式 v1 的发布门槛。

测试时应模拟：

- 原电脑全部离线。
- 删除原客户端 SQLite。
- 删除原客户端缓存。
- 仅保留：
  - 百度网盘远端 Repository。
  - 恢复凭据/恢复包。
  - 独立恢复工具或新安装客户端。

必须能够：

1. 定位 Repository。
2. 验证格式版本。
3. 解锁必要加密元数据。
4. 重建设备/计划/快照目录。
5. 浏览历史。
6. 下载并恢复指定文件或完整验收集。
7. 对恢复后原始内容执行强摘要验证。

## 22.1 恢复包

建议包含：

- Repository 定位。
- repository_id。
- 格式版本。
- 密钥恢复材料或安全封装。
- 必要 KDF 参数。
- 校验信息。
- 使用说明。
- 客户端/独立恢复工具兼容说明。

恢复包应保存在独立安全位置，不能只存在于由同一密钥加密的 Repository 内。

# 31. 数据不变量

必须长期保持：

1. `FileInstance` 的身份依赖设备、BackupPlan 和原始相对路径语义。
2. `Content` 不包含唯一原路径假设。
3. 一个 `Content` 可以拥有多个 `Representation`。
4. 一个 `Representation` 可以临时拥有多个 `Object`。
5. Snapshot 只能引用已经确认可用或符合协议的对象关系。
6. 任何“已保护”状态都必须可追溯到一个成功提交的 Snapshot。
7. 本地数据库不是唯一恢复真相。
8. 远端 Snapshot/Manifest 必须拥有格式版本和完整性校验。
9. 新客户端可以迁移旧格式；旧客户端遇到未知新格式时只读或拒绝写入。
10. 删除 Object 前必须证明不再被任何保留 Snapshot 的引用闭包需要。
11. 设备本地时间不能作为跨设备冲突裁决的唯一依据。

# 32. 错误分类

| 类别 | 示例 | 行为 |
| --- | --- | --- |
| 授权 | Token 过期、权限撤销 | 自动刷新；失败则要求重新授权 |
| 配额 | 网盘空间不足 | 暂停新增上传，保留历史，不静默删除 |
| 网络 | 断网、超时 | 保存断点，退避重试 |
| 限流 | API 429/服务繁忙 | 指数退避 + 抖动 + 降并发 |
| 源文件 | 无权限、文件占用、读取变化 | 明确路径，稳定重试，不假成功 |
| 源设备 | 外接盘离线 | 标记离线，不产生删除记录 |
| 缓存 | 临时磁盘不足 | 暂停转换任务，提示释放空间 |
| 数据 | 摘要不一致、对象损坏 | 禁止标成功，进入修复流程 |
| Manifest | 清单损坏/缺失 | 阻断受影响 Snapshot，尝试冗余副本 |
| 密钥 | 密钥缺失/错误 | 无法解密，禁止破坏性迁移 |
| 格式 | 仓库版本过新 | 只读或拒绝写入 |
| 并发 | 多设备并发提交 | 唯一记录、幂等合并，不覆盖 |
| 恢复 | 目标路径冲突 | 预览后由用户选择策略 |

# 33. 非功能要求

## 33.1 正确性

发布阻断级要求：

- 错误显示“当前版本已保护”为 0。
- 内容误去重为 0。
- 已声明恢复成功的文件摘要必须匹配。
- 崩溃不得产生虚假成功 Snapshot。
- 加密策略不得错误复用明文表示。
- 损坏 Object 不得继续显示健康。

## 33.2 性能

以百万级 FileInstance 为设计基线，正式指标需固定测试环境后确定。

建议初始目标：

- 常用本地筛选首屏 < 1 秒。
- 常用索引查询 P95 < 2 秒。
- 内存和缓存使用有界。
- UI 不等待全库一次性加载。
- 使用分页、后台索引和背压。

不提前承诺通用扫描 MB/s 或上传速度，必须根据实际数据集测量。

## 33.3 可观测性

必须提供：

- 最近成功扫描。
- 最近成功 Snapshot。
- 最近远端同步。
- 最久未保护时长。
- 当前逻辑待处理量。
- 实际待上传量。
- 去重复用量。
- 错误计数。
- API 退避状态。
- 本地缓存用量。
- Repository 健康。

## 33.4 隐私

- Token 存入 OS 安全凭据能力。
- 主密钥和恢复材料不写明文日志。
- 日志默认脱敏路径。
- 诊断包导出前展示内容类型。
- 崩溃转储避免包含明文密钥。

# 37. 关键验收测试

| 编号 | 输入/动作 | 必须结果 |
| --- | --- | --- |
| AT01 | A 先备份，B 有同内容异名文件 | B 不重传有效载荷；B 路径可独立恢复 |
| AT02 | 同名同大小但内容不同 | 不发生错误去重 |
| AT03 | 修改内容但人为保持 size/mtime | 严格校验能发现变化 |
| AT04 | 同内容分布在多个目录 | 数据复用，路径全部保留 |
| AT05 | 已备份文件修改 | 当前变为待保护，旧版本仍可恢复 |
| AT06 | 文件只改名/移动 | 内容不重传，两个历史快照路径正确 |
| AT07 | 文件夹存在排除/失败项 | 不显示全部保护，统计准确 |
| AT08 | 空文件、空目录、全排除目录 | 状态和恢复结果正确 |
| AT09 | 两设备同时首次上传同内容 | 可有冗余 Object，但无覆盖/悬空引用 |
| AT10 | B 发现 A 已有内容但尚未提交路径 | 显示可复用待登记 |
| AT11 | 上传中断网并重启 | 从可确认断点继续或安全重试 |
| AT12 | 服务端 upload session 失效 | 安全重建，不丢其他已确认对象 |
| AT13 | 压缩/加密暂存丢失 | 不混用旧分片与新 Representation |
| AT14 | Object 上传完成、Manifest 提交前崩溃 | 不显示已保护，重启后安全继续 |
| AT15 | Snapshot 提交响应丢失后重试 | 幂等，不产生矛盾记录 |
| AT16 | 授权过期/空间不足/限流 | 正确分类、暂停或重试，不丢历史 |
| AT17 | 四种模式备份并恢复 | 原始摘要全部一致 |
| AT18 | 已有明文但新任务要求加密 | 新建合规加密 Representation |
| AT19 | 错误密钥或被篡改密文 | 恢复失败且不输出冒充成功的文件 |
| AT20 | 恢复目标存在同名文件 | 先预览，默认不覆盖 |
| AT21 | 原设备和本地 DB 均不存在 | 仅凭远端和恢复材料可重建恢复 |
| AT22 | 删除一个被多个快照引用的 Object | 所有受影响快照联动标风险 |
| AT23 | 外接硬盘被拔出 | 标源离线，不记录整盘删除 |
| AT24 | 本地删除文件 | 新快照记录消失，历史仍可恢复 |
| AT25 | 改变排除规则 | 与用户主动删除区分 |
| AT26 | GC 时存在离线/在途写入者 | 无安全屏障则拒绝物理删除 |
| AT27 | 长时间离线设备 | 其最后完整恢复点不被其他设备挤掉 |
| AT28 | 旧客户端打开新仓库格式 | 只读或拒绝写入 |
| AT29 | 百万级索引筛选 | 固定环境下达到性能目标且资源有界 |
| AT30 | 扫描既有网盘文件 | 未确认前不视为已纳入保护 |
| AT31 | 多设备系统时钟偏移 | 不按时钟简单覆盖记录 |
| AT32 | 抽样验证 | 明确标示 V2，不宣传全部数据完整 |
| AT33 | 完整恢复验证 | 对指定 Snapshot 全部数据校验 |
| AT34 | 备份持续写入文件 | 不产生混合版本假成功 |
| AT35 | 更改口令 | 仅密钥封装更新，不误称完成数据轮换 |
| AT36 | 设备退出/密钥轮换 | 明确已有 Token/密钥的撤销边界 |
| AT37 | 大量扩展名变化/高熵改写 | 触发异常保护，保护异常前恢复点 |
| AT38 | 大量删除但源其实离线 | 不误触发真实删除历史 |
| AT39 | 全局重复视图 | 相同 Content 能跨设备聚合且 Representation 数正确 |
| AT40 | 百度 Adapter 被替换为测试 Adapter | 备份核心逻辑无需重写即可跑通主要流程 |

# 44. 当前推荐结论

在未完成 G0 和 D01–D06 确认前，推荐先按以下方向推进：

```text
产品：备份，不做双向同步
平台：Windows
仓库：一个受信任安全域
存储：百度网盘作为第一个 Storage Adapter
去重：Repository 内 Content 级跨设备去重
增量：正式 v1 文件级增量
状态：五维状态模型
事务：Object 确认 → Manifest → Snapshot 提交
加密：仓库级密钥体系 + Representation
并发：无锁文件，接受安全的临时冗余
恢复：全新设备恢复是发布门槛
安全：历史保护 + 健康验证 + 异常/勒索保护
删除：正式首版不自动物理 GC
扩展：保留 Coordination Service / CDC / 多云接口
```

这套定义能同时满足“少传重复文件”“看得懂每个文件是否备份”“不同设备共享备份状态”“可加密/压缩”“断点续传”“历史恢复”和“未来扩展”的目标，同时避免为了追求表面上的绝对去重而牺牲真正的可恢复性。
